This page explains which data Deepslate stores when you use the platform, how you control it, and how **Zero Data Retention (ZDR)** works for sessions on the Realtime API.

## Standard data handling

By default, Deepslate stores call data so you can review and analyze your calls in the Deepslate platform, for example to check transcripts, debug a conversation, or improve your system prompt.

| Data | Stored by default | Purpose |
|------|-------------------|---------|
| Session metadata (start and end time, duration, model) | Yes | Billing, usage reporting, call overview |
| Technical telemetry (latency, generation time, VAD events) | Yes | Performance monitoring and debugging |
| Conversation content (transcripts, chat history, tool calls) | Yes | Call review and analysis in the platform |
| Audio recordings | Configurable | Call review in the platform |

<Info>
**Your data is not used for model training without your consent.** Deepslate does not train its models on your call data unless you have explicitly agreed to it.
</Info>

### Retention periods and deletion

To have stored call data deleted, contact us at [info@deepslate.eu](mailto:info@deepslate.eu). When your contract ends, your data is deleted in accordance with your Data Processing Agreement (DPA).

If you need conversation content to never be stored in the first place, use Zero Data Retention.

## Zero Data Retention

Zero Data Retention is designed for workloads with especially sensitive data, for example in insurance, banking, or healthcare. With ZDR enabled, conversation content is processed exclusively in volatile memory, only for as long as needed to run the session in real time, and is **never persisted** by Deepslate.

<Note>
Zero Data Retention is an **Enterprise feature** and applies to the **Realtime API only**. To enable it for your organization, [contact us](mailto:info@deepslate.eu).
</Note>

### Availability

| | Covered by ZDR |
|---|---|
| Realtime API (WebSocket) | Yes |
| SDKs and plugins (LiveKit, Pipecat) | Yes, as they connect through the Realtime API |
| Assistants and Agents (inbound and outbound phone calls via the platform) | No |

### What is never stored

When ZDR is active for a session, Deepslate does not store:

- Audio (neither the caller's nor the model's)
- Transcripts and chat history
- System prompts and inference configuration content
- Tool names, tool arguments, and tool results
- The client IP address

### What is still stored

To operate and bill the service, Deepslate keeps a minimal set of technical data that contains **no conversation content** and nothing derived from it:

| Data | Examples | Purpose |
|------|----------|---------|
| Session metadata | Session ID, state, start and end time, duration, model | Billing and usage reporting |
| Usage records | Feature types and unit counts | Billing |
| Technical telemetry | Event types and timestamps, turn IDs, tool call IDs, generation time, gaps between turns, audio duration, realtime factor | Performance monitoring |

### How to enable it

<Steps>
  <Step title="Request access">
    Contact us at [info@deepslate.eu](mailto:info@deepslate.eu). Once ZDR has been enabled for your organization, the option becomes available in the Deepslate platform.
  </Step>
  <Step title="Turn on Zero Data Retention">
    In the Deepslate platform, open your organization's **Basic Data** page and turn on **Zero Data Retention**. The setting applies to all Realtime API sessions of your organization, including sessions opened through the SDKs and plugins.
  </Step>
  <Step title="Optional: set retention per session">
    If you connect to the WebSocket API directly, you can also set the retention level for a single session using the `X-Deepslate-Data-Retention` header. See [Per-session override](#per-session-override).
  </Step>
</Steps>

### Per-session override

Add the `X-Deepslate-Data-Retention` header to the WebSocket handshake to set the retention level for one session:

```javascript
import WebSocket from 'ws';

const ws = new WebSocket('wss://app.deepslate.eu/api/v1/vendors/{vendorId}/organizations/{organizationId}/realtime', {
  headers: {
    'Authorization': 'Bearer YOUR_API_KEY',
    'X-Deepslate-Data-Retention': 'none'
  }
});
```

| Value | Effect for this session |
|-------|-------------------------|
| `none` | Zero Data Retention. No conversation content is stored. |
| `chat-history` | No audio is recorded. Chat history follows your organization settings. |
| `all` | No change. Your organization settings apply. |

The header can only make retention **stricter** than your organization settings, never looser. For example, if ZDR is turned on for your organization, sending `all` does not turn it off.

An unknown or empty value rejects the handshake with HTTP `400` before a session is created.

### Limitations

<AccordionGroup>
  <Accordion title="Limited support and debugging" icon="life-ring">
    Because Deepslate does not have the conversation content of ZDR sessions, we cannot inspect them when you report an issue. Troubleshooting is limited to the technical telemetry listed above. To help us debug, include the session ID and a description of what happened.
  </Accordion>

  <Accordion title="No call review in the platform" icon="eye-slash">
    ZDR sessions do not show transcripts, chat history, or recordings in the Deepslate platform. Tool calls appear with a generic label instead of the tool name.
  </Accordion>

  <Accordion title="Keeping your own records" icon="floppy-disk">
    If you need a record of the conversation, store it on your side. Your client can request the full conversation at any time during the session with [`ExportChatHistoryRequest`](/api-reference/realtime). The SDKs and plugins expose the same capability as chat history export.
  </Accordion>
</AccordionGroup>
